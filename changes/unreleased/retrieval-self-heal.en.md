- **A damaged search index no longer switches search off for good: the extension resets it, and Settings says what happened.** A crash while the index was being built could leave its newest files empty; the search service then stopped at every start, and Settings › Search extension only said the search tool "cannot be found" and to check that it is enabled in DSH. Now the search extension checks its index before DSH starts the search service, moves an index the service could not open aside (it is kept, never deleted) and starts on an empty one. When the extension is installed but its service is not running, Settings says "The search extension is installed, but its search service did not start", with the likely reason when it is known ("The index was damaged and has been reset; build the index again.") and one Repair, which moves the index aside and clears this library's index record; then restart DSH and build the index again. Material rows whose pages were in the old index say "Index needs rebuilding" instead of claiming they are indexed, and the next build sends every page again. The "check that it is enabled in DSH" advice stays only for a search tool that is really gone. The local index record is now written to disk before it replaces the old one. Not verified: the repair button and the restart in the DSH desktop app (the card was checked as rendered components and in tests; the check and the service start were run with DSH's own program on a copy of a real broken index); the check of a table whose files look whole but which LanceDB cannot open runs only where the extension's own LanceDB is installed, so CI skips those tests; an index whose newest manifest is whole but whose data files are damaged is not caught by the check (Repair is the way out); English and dark screenshots of the material rows.
