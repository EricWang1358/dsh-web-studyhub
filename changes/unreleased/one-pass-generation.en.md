- **The default way questions are written has changed: coverage runs of multiple-choice questions are now written in one pass.** The setting is 出题方式 under 高级生成控制 in 设置: 「快速铺题（默认）」 is one pass; choose 「逐题精出」 there to go back to the staged pipeline. A library that had 采纳审阅建议 (apply review suggestions) turned on and never chose a 出题方式 stays on 「逐题精出」 until you choose. One pass does not use 每批题数 (batch size), the 规划考点与答案设计 reasoning level or 采纳审阅建议; they still apply to the staged pipeline.
  - **The default now writes about twice as many questions for the same material.** One pass at 标准 plans about 14 questions per 10,000 characters (1 to 6 for every part of a section of about 4,250 characters), where 「逐题精出」 plans 6; 精简 and 完整 are about 7 and 23 (scaled from the staged 3 : 6 : 10, not measured). A section is asked at most one round's questions (30), so a section longer than about 21,000 characters at 标准 (13,000 at 完整, about 26,000 at 精简) gets 30 and is below that density; it still gets more than with 「逐题精出」. The staged levels are unchanged. The bounds of one run are unchanged too (500 questions in all, 400 from one material), so with one pass a selection of more than about 350,000 characters reaches them sooner, and the plan says it was capped. The words of each 覆盖强度 level, the suggested number, the question forecast and the token estimate all use the density of the way the run will be written. 深度定制 is unchanged: its runs are cut, counted, estimated and written with the staged pipeline whatever 出题方式 says, so a plan made earlier is cut into the same runs.
  - **How one pass writes.** The sections of each round's plan are packed into portions of at most about 9,000 characters and 12 questions (a section is never cut, except that a section asked for more than 12 questions is written in pieces); one call per portion writes every section's full cards, told the number per section and never a total. The write call asks for scenario questions: what a serious student must be able to use (a rule with its condition or exception, a distinction, a cause, a procedure), a short concrete scenario whose decisive condition changes the answer, and an explanation in four moves. The program then checks each card without a model: its quote must stand in its section, exactly one option is correct, no second card on the same quote or objective, at most the section's quota, and the options are shuffled by the program. A section left with no card is asked again once, alone. A card whose correct option is more than 25% longer than the longest wrong one is sent back once for its options to be rewritten (one call per portion; the correct option must stay the same one) and dropped if it still stands out. The review judges at most 7 cards per call, each from its quote and about 350 characters on each side, never the whole material; a card it fails is dropped. A review call that fails is tried once more, and only that batch of cards is given up; a portion that lost all its cards that way is written again by the next fill round. Cards on the same objective or quote from portions written at the same time are merged before each save, and one more call per round groups the cards that test the same fact in other words, keeping the first of each group; the program accepts only groups of at most 3 cards from the same or neighbouring sections, and ignores a reply that would remove more than a tenth of the round. A card merged away leaves its section covered by the card that stays, and is kept whole (options, explanation and quotes) in the draft's list of dropped questions. A round that is stopped or runs out of time saves its cards already merged by the program. A reply that cannot be read as JSON is asked for again once before the work it carries is given up. The draft keeps the same records as before (each card's section, the plan's targets and what became of each, sections still short as plan-short failures, rounds and round limit, failures in words, token usage) and records which way it was written; every call is a step in the 任务 console. The forecast of a one-pass run is a range (the plan is the upper end). The token estimate prices one pass as it runs (per portion one write and a review per 7 questions, one merge per round); its upper end also counts a rewrite of the options per portion, a second ask for every section and a second try of every review. The machine's estimate correction is learned from the staged pipeline: a one-pass run does not change it, and it is not applied to a one-pass estimate (a round of a one-pass run that is written by the staged pipeline still teaches it). Other question types, case papers, runs by a number of questions and the rewriting of failed targets in a top-up still use the staged pipeline, as does any run when 「逐题精出」 is chosen; continuing a draft or topping it up keeps the way it was started, so a draft from an earlier version goes on with the staged pipeline. Not verified: runs of the product code against a real model (only the recorded prototype measurements and fake-model tests), PDF material, and the question counts of 精简 and 完整 with one pass.
