# 补入已有题库

「把这份资料的缺失考点补进某个题库」使用 `supplement`，而不是让主会话把生成、等待、发布拆成多轮确认。

```json
{"action":"supplement","payload_json":"{\"deckId\":\"目标题组的完整 ID\",\"sourceIds\":[\"资料 ID\"],\"count\":5,\"kind\":\"flashcard\",\"focus\":\"与已有题目比较后确认缺失的课堂考点\"}"}
```

先比较老师讲授的概念与目标题库的实际题目，再选择缺口、题数及前置关系。`source.coverage` 的直接引用数只能帮助定位证据，不能代替语义覆盖判断；标题里的数字也不是补题数量。需要前置关系时，用 `capture.requiredBy` 或 `card.link` 保存明确的卡片关联。

`supplement` 要求明确、未归档的普通题组。用户要求补入该题组，已授权本地生成、审核及发布；插件依次运行这些步骤，阶段 JSON 由插件回收，不注入主会话。原有 `generate` 保持只生成草稿的行为。

通过审核的题目并入原题组，完整成功后移除内部草稿检查点。最终任务回执包含 `publication.deckId`、`added`、`total` 和 `remainingDraftId`；只有实际持久化的数量可以报告为已补入。原题 ID、复习记录及历史保持不变，不创建另一个独立题库。

目标被删除或归档、草稿冲突、取消或审核失败时，不自动重跑，也不退回新建题库。未通过或未完成的工作保留可恢复的检查点并明确报告，不能伪装成全部成功。零通过时任务失败；部分通过时报告新增数及未补足数量。需要恢复部分生成时可以提供 `resumeDraftId` 和当前 `draftVersion`，目标必须与 `deckId` 一致。

`job.wait` 可用于完成用户已授权流程的一次有界等待（最多 60 秒），不要求用户额外说「等」。超时后返回控制，最终通知给出结果；禁止轮询循环或重复入队。
