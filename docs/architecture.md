# StudyHub architecture

This page is for developers who extend StudyHub or build on its plugin APIs. For installing and using StudyHub, see the [README](../README.md).

Since 2.0, StudyHub has been a set of separately installable capability plugins for DeepSeek Harness (DSH). All of them share one runtime.

## At a glance

- **Plugins.** The package ships a workbench plugin and six capability plugins: runtime, materials, bank, study, generation and audio. They share one `studyRuntime` service, so installing several of them never registers a context or tool twice.
- **Runtime and contexts.** `StudyRuntime` (`lib/runtime.js`) hosts 19 contexts, each with a versioned API such as `bank.v1`. A context owns its records, declares its dependencies and reaches other contexts only through granted operations.
- **Library.** Each DSH session resolves one study library. An atomic, content-addressed shard store (`lib/store.js`) saves it. Retained original files sit beside it under `attachments/materials/`.
- **Data formats.** Decks stay JSON. Sources keep their original PDF, Word (.docx), PowerPoint (.pptx), Markdown, HTML or TXT file and expose versioned text projections.
- **Interface.** React sources in `ui/` build into DSH client modules (`lib/client*.js`). Optional views load lazily.
- **Models.** Read operations never need a model. An operation that does declares `requiresModel`; called without a model, it returns `{ available: false, reason: 'model_unavailable' }`.

### Full install

`cordis.patch.yml` inserts the workbench with `modular: true` and all six capability plugins; study and generation get `independent: true`. Each optional context therefore comes from exactly one component. This is why the full install lets you turn components on and off separately in DSH's plugin manager.

### Load plugins independently

```js
import * as materials from '@ericwang1358/dsh-daily-flashcard/plugins/materials';
import * as bank from '@ericwang1358/dsh-daily-flashcard/plugins/bank';

ctx.plugin(materials);
ctx.plugin(bank);
```

Each plugin acquires its contribution to the shared `studyRuntime` service:

- Reference ownership prevents duplicate service and tool registrations when standalone plugins and the workbench are installed together. This includes separately installed copies of the package, because the scope is keyed by `Symbol.for('studyhub.runtime.scope.v1')`.
- Unloading the last owner of a context removes that context and its tools. Its durable library records remain.

### Release archives

`npm run release:pack` (`scripts/release-alpha.mjs`) builds the release assets:

- the complete package;
- one archive per capability plugin, named `@ericwang1358/dsh-study-<domain>` for runtime, materials, bank, study, generation and audio;
- the search extension `@ericwang1358/studyhub-retrieval`, with the same version;
- the English and Chinese setup pages;
- a `SHA256SUMS-<version>.txt` checksum list.

The script does not build or verify. The release coordinator runs those steps first.

## The runtime service

### Call the runtime from a plugin

```js
ctx.inject(['studyRuntime'], async c => {
  const api = c.studyRuntime.forLibrary(absoluteLibraryPath);
  const contracts = api.describe();
  const capabilities = api.capabilities(requestServices);
  const result = await api.invoke('bank.v1', 'get', { deckId }, requestServices);
});
```

`forLibrary(path)` returns a facade with five methods:

| Method | Use |
| --- | --- |
| `invoke(api, operation, args, services)` | Call a qualified operation, such as `bank.v1` `get` |
| `call(action, args, services)` | Call a public action name, such as `bank.get` or `generation.selection.supplement` |
| `describe()` | Every installed context with its operations, input and output schemas and `requiresModel` |
| `capabilities(services)` | The same, plus whether each operation is available with these request services |
| `register(definition)` | Add your own context to this library's runtime (see [Add a capability](#add-a-capability)) |

`runtimeForLibrary(path)` returns the `StudyRuntime` itself, for example to call `registerParticipant`. The `runtime.describe` and `runtime.capabilities` actions expose the same contracts to the UI and agents.

One runtime serves each library. It is reused across requests and compact tools.

### Request services

Request services are per-call context. They are never persisted in domain records. They include:

- `complete` and `completeLight` (the session's model route);
- `language`, set from the request's `uiLanguage` (see [Interface language](#interface-language));
- `signal` (cancellation) and `workOwner`;
- `notify` and `sessionId` (notices to the session);
- `tokenMeter` (DSH's token estimator, when the host has it);
- `retrieval` (the host retrieval port);
- `audioGate`.

### Library binding

The workbench resolves the library from the session's workspace (`binding` in `lib/host.js`), in this order:

1. the `root` saved in `.dsh-study-binding.json` in the workspace;
2. the workbench config `libraryRoot`;
3. the workspace itself if it contains `study-workspace.json`, otherwise `<workspace>/.dsh-study`.

### Contexts and public APIs

Materials, bank, study, authoring, generation and audio are the optional contexts that the capability plugins supply in a full install. Learner, workflow data and skeleton data are data-only: they own records and expose only `state.read`, so they have no folder under `lib/contexts/`.

| Authoring | `authoring.v1` | – | Publication (`draft.publish`, `draft.publish.quick`), deck import, merge and split, and validation, as transactions across content and study records |
| Generation | `generation.v1` | `selectionJobs` | Generation, supplement and repair jobs, independent review, publication through authoring, passage supplementation, retrieval providers and page-translation jobs |
| Audio | `audio.v1` | `audioResults` | Transcription, subtitle import, transcript corrections, live class recording and MinerU PDF conversion, with their jobs; publishes through materials and generation when they are installed |
| System | `system.v1` | `settings`, `focus` | Settings and the focus record; the update check, the experimental-features switch, Jev settings and the usage frequency record |
| Notifications | `notifications.v1` | `inbox` | Inbox records and read markers |

Earlier transition responsibilities now have lasting owners:

| Responsibility | Owner |
| --- | --- |
| Coach and prepared practice | coach and learner |
| Article drafts | notes |
| Conversation capture and ingest | recording |
| Learning flows | workflows and workflow data |
| Outlines | skeleton and skeleton data |
| Oral practice | study |
| Snapshot and inbox presentation, administrative backups | library |

The transition container and the legacy authority are removed.

### Dependencies, grants and transactions

- The dependency graph is acyclic. Settings, notifications and the data-only contexts form the bottom layer. Bank reads material evidence and study reads bank data. Authoring coordinates content and referential updates, generation publishes through authoring, and audio can invoke generation. Library supplies presentation joins.
- `lib/runtime/domain-contracts.js` declares each context's owned fields, reads, exact operation grants and per-action write sets. A few extra dependencies live in `builtins.js` (generation on authoring, audio on generation, jobs on audio, library on coach and jobs).
- A context can call another only through a declared dependency and, for built-ins, a granted operation. Domains never receive the `StudyService` facade or the unrestricted store.
- Cross-context transactions use named participants under one storage lock.
- ESLint (`eslint.config.js`, for `lib/contexts/**`) and `tests/architecture-boundaries.test.mjs` check actual imports and runtime declarations, not an illustrative graph.

Shared pure functions remain ordinary modules; splitting every helper is not a goal. Mutable work belongs to one runtime, which supplies named service projections to the domains that need them.

### Action aliases

A public action can name a higher-priority alias for an installed aggregate provider. Qualified domain operations keep their own implementations. Equal-priority aliases are registration conflicts.

| Action | Materials alone | When the richer provider is installed |
| --- | --- | --- |
| `materials.links.list` | Answers with an unavailable bank state | Bank's authoritative link query; unloading bank restores the fallback |
| `materials.pages.cards` | Answers with an unavailable library state | Library's aggregate |
| `source.import`, `source.courses.set` | Materials' own operations | Library's aggregate |

### Agent tools

StudyHub registers these tools on DSH's tool registry. The five per-context tools (`lib/runtime/tools.js`) take an `operation` plus typed arguments instead of a serialised argument string. Each one appears when its context is installed, whichever plugin supplies that context, and disappears with the context's last owner.

| Tool | Comes with | Operations |
| --- | --- | --- |
| `study_capabilities` | Any StudyHub plugin | Discovery: installed APIs, operation schemas and model availability |
| `study_materials` | The materials context | `document.import`, `document.get`, `document.list`, `document.attach`, `original.*`, `selection.resolve`, `selection.ask`, `outline.*`, `links.list`, `pages.cards`, `enrich` |
| `study_bank` | The bank context | `list`, `get`, `cards`, `append` |
| `study_practice` | The study context | `review.start`, `review.get`, `review.reveal`, `review.answer`, `review.move`, `review.end`, `exam.report` |
| `study_generate_selection` | The generation context | `selection.supplement`, `selection.get`, `selection.commit`, `selection.review` |
| `study_audio` | The audio context | Results, jobs, audio settings, import, retry, subtitle import, correction review and live recordings |
| `study_workspace` | The workbench | The transition entry: any study action by name, with `payload_json`. It refuses `usage.frequency.*`, which belongs to the learner's panel only |

### Interface language

- An action envelope may include `uiLanguage: "en" | "zh"`. The runtime removes this reserved field before validating the domain payload, and passes the language on as a request service.
- Without request metadata or an explicit service language, a call keeps the legacy Chinese default.
- A request never changes another request's language or the library's stored content.

`lib/application-messages.js` translates only application-owned error, progress and notification fields. Sources, cards, notes, IDs, filenames and unknown provider evidence stay unchanged.

Other language rules:

- Background work keeps the language it started with for its notifications.
- New transcript scaffolding may use English. Readers accept both existing Chinese and new English transcript markers.
- Explicit bilingual translation targets stay independent of the interface language.

## Document-to-deck flow

1. `materials.document.import` takes one absolute file `path` or uploaded `dataBase64`, plus a filename or `format`.
   - Formats are `pdf`, `docx`, `pptx`, `md`, `html`, `txt` and converter `json`.
   - Size limits are one constant per format in `lib/office/limits.js`: 8 MB for PDF and text formats, 40 MB for Word, PowerPoint and converter JSON.
   - Text files must be UTF-8.
   - Word and PowerPoint are read server side by a built-in ZIP/XML reader (`lib/office/`, no dependency). A .docx becomes one Markdown-like source. A .pptx becomes one source per slide, with `document.page` locators like PDF pages.
2. `materials.document.get` returns the document and revision identity, the projected source IDs and an original preview descriptor. `materials.document.bytes` supplies verified original bytes for the standalone preview.
3. `materials.selection.resolve` verifies the visible `quote`, optional `prefix`/`suffix`, source and document identity, the revision and optional offsets or PDF page. It reports `resolved`, `ambiguous`, `stale` or `missing`.
4. `materials.selection.ask` answers from the checked passage and nearby source evidence when a request model is available. `generation.selection.saveAnswer` saves such an answer as one linked flashcard without calling a model.
5. `generation.selection.supplement` needs a resolved `selection`, an existing `deckId`, a stable `operationId` and `expectedVersion`. `count`, `kind` and `focus` are optional. It writes questions, reviews them independently and appends the accepted ones.
6. `materials.links.list` derives associations and current explanations from committed card JSON. A passage may link to several cards across decks.

```js
const selected = await api.call('materials.selection.resolve', {
  documentId, revision, quote, prefix, suffix,
});
const destination = await api.call('bank.get', { deckId });
const result = await api.call('generation.selection.supplement', {
  selection: selected.selection,
  deckId,
  expectedVersion: destination.version,
  operationId: crypto.randomUUID(),
  count: 3,
  kind: 'flashcard',
}, requestServices);
```

### Run a supplement as a background job

An interface that must not wait for the model, such as the reader's learning panel, calls `generation.selection.start` with the same arguments.

- It returns at once with a job handle: `jobId`, `operationId`, `status` and `job`.
- The work is the same plan, write, independent review and atomic append. It runs as an ordinary `supplement` job (`origin: 'selection'`) in the library's job table and queue.
- Like other jobs, it has steps, a token estimate and usage, a stop (`job.cancel`) and a notice to the session. When it adds questions, an inbox letter opens at the first new card.
- The same `operationId` never starts twice: a running job is returned, and a finished one replays its receipt.
- The same passage for the same deck is refused while a job for it runs (`DUPLICATE_SUPPLEMENT`).
- `generation.selection.status { operationId }` reads the job back, rebuilt from the saved operation after a restart. `generation.selection.jobs { documentId }` lists a document's jobs.
- `usage.estimate { feature: 'selection', ... }` states the expected tokens before the job starts.
- Starting again under a stopped or failed `operationId` continues from what it saved. A conflict retries the save against the deck's current version, and saved candidates are reviewed again rather than rewritten. Anything else starts over.

### Commit and recovery rules

- The append transaction checks the destination version and the material evidence while holding the library lock.
- It preserves existing card IDs and progress, appends new cards with additive `selections` metadata and records a receipt once.
- Replaying an already committed operation returns its receipt, even if the document has changed since.
- Reusing an operation ID with different content is rejected.
- Failed reviews keep the written candidates, and conflicting commits keep the approved cards. Inspect them with `generation.selection.get`. Use `generation.selection.review` to repeat an independent review, or `generation.selection.commit` with a newly read destination version to retry publication.
- Neither path authorises unchecked additions or silently retargets an outdated source selection.

## Retrieval providers (large textbooks)

StudyHub has no search index of its own.

- A converted textbook is imported through the same `materials.document.import`. It becomes page sources with `document.chapter` for the heading each falls under, and no original is retained.
- Choosing from it uses chapter groups (`groupSourcesByDocument` in `lib/source-groups.js`).

Search is delegated through one contract in `lib/retrieval.js`:

```js
retrieve({ query, sourceIds?, course?, limit, signal? }) -> [{ sourceId?, page?, document?, text, score }]
```

There are three providers:

| Provider | What it is |
| --- | --- |
| `mcp:<tool>` | A tool that DSH's MCP client registered as `mcp__<server>__<tool>`. The host adapter (`lib/retrieval-host.js`, wired in `lib/host.js` `serviceFor` as the `retrieval` request service) lists tools with `ctx.tools.schemas()` and runs one with `ctx.tools.execute({ callId, name, arguments, signal })`. The result value `{ content, structuredContent? }` is mapped by `hitsFromMcpResult`. Only profile-level servers are visible |
| `service` | Another plugin registers the Cordis service `studyRetrieval` with `retrieve(request)`. StudyHub reads it with `ctx.get('studyRetrieval')` |
| `builtin` | No retrieval: the selection is sent as before |

How the choice is used:

- The choice is stored in `$DSH_HOME/study/retrieval.json`, with no secrets. It is managed with the generation context's `retrieval.status`, `retrieval.set`, `retrieval.test` and `retrieval.preview`. The `retrieval.index.*` operations plan, build, report on and cancel an index.
- Contexts reach the host through `ports.retrieval` (`{ tools(), call(), service() }`), never through `ctx` itself.
- The jobs context reads a finished DSH sub-agent's final reply through `ports.sessions.lastReply(childId)` (`lib/session-reply.js`, over `ctx.get('sessionQuery')`, passed to the runtime as the request service `sessionQuery`); it never throws and answers `null` when the session cannot be read.
- `generate` narrows a selection to the retrieved pages (`narrowSelection`) when it is above 150,000 characters or the request asks for retrieval, and a provider and a topic (`focus`) are set. It records `job.retrieval`.
- The guided flow uses retrieval to rank topics (`lib/workflow-retrieval.js`).

The search extension is a companion bundle (`packages/studyhub-retrieval`), published as a release asset by `npm run release:pack`:

- Its plugin calls `ctx.plugin(mcpClient, config)` for `mcp-local-rag`. The command is `process.execPath`, and the server entry is resolved next to the package, so no configuration file is edited.
- `lib/retrieval-extension.js` installs and removes it through `ctx.pluginManager.installBundle` and `removeBundle`. The asset is checked against the release's SHA-256 list, and dependency builds need `approvedBuilds` confirmation.
- `lib/retrieval-index.js` indexes a course page by page under `studyhub://source/<id>`. Indexing is incremental.
- The host handler adds `retrieval.extension.*` and the `extension` field of `retrieval.status`.

See [large documents](large-documents.md) for the formats, limits and recommended tools.

## Preview integration

- The workbench opens retained originals through DSH's public `sidebarRight.openResource` file resources. It contributes learning actions to `sidebar.right.tab.document.actions` (`ui/document-preview/native.jsx`).
- A focused target's identity binds a captured selection to its current document tab.
- DSH's built-in HTML preview uses a sandboxed frame. An optional, inert **Study HTML** renderer (`study-html`) supplies selectable HTML and passage marks through the public preview registry. The original renderer remains selectable in DSH.
- The workbench's own document view renders Markdown tables, sanitised HTML and TXT with passage marks. For PDF it shows the retained original and a clearly labelled, selectable extracted-page view. Native PDF, Markdown and TXT keep the host viewer.
- The study renderer removes HTML scripts, event handlers, embedded browsing, forms and external resource loading. Selection validation uses source evidence rather than trusting rendered DOM text alone.

## Storage

### Store format

- `study-workspace.json` is a small manifest: scalar fields plus the ordered list of shard files under `shards/`.
- Each source, deck, draft and practice run is its own shard, attempts are chunked, and the small coach logs are one shard each.
- Shard names carry a content hash. A commit writes only the changed shards, then atomically replaces the manifest.
- Contexts register collection descriptors without editing the core field list. Unknown extension shards, scalar values and older manifest arrays survive reads and unrelated writes, even when their plugin is absent.
- A restore first saves the current library as `backups/study-workspace-before-restore-<time>-<id>.json`.

### Older libraries

- Supported older libraries normalise missing collections on read. They upgrade on a later write, which keeps a pre-upgrade copy in `backups/`.
- The current store version is 4, which gives courses stable ids: `course-` plus a hash of the normalised name, derived on read. Every commit keeps `courseIds`/`courseId` in sync with the legacy course names, which stay authoritative for older readers (`lib/courses.js`).
- Old sources and decks may lack optional document or question metadata and remain usable. `materials.enrich` fills missing deterministic values and reports facts it cannot establish.
- Old PDF imports that discarded originals remain available as extracted text. To gain an original preview, attach the original file explicitly.

### Job archive

- `job-archive.json` sits next to the library file (`lib/job-archive.js`, one writer per library, atomic replace). It holds the read-only records of finished jobs the learner archived (and of finished jobs the in-memory list trimmed): the job's contract as the 任务 console draws it, bounded, with no output, keys or library path. It keeps the newest 200 records of the last 90 days; the oldest fall off and an audio batch's working copy goes with them.
- Archiving deletes no file. Audio recovery (`lib/contexts/audio/worker.js`) skips archived batches, singles, conversions and legacy cards, so a restart never brings them back into the list; `job.unarchive` reads the folder again. The snapshot's `archivedJobs` carries the records; `docs/job-contract.md` has the operations.

### Original files

- Retained originals live at library-relative `attachments/materials/<sha256>.<format>` paths.
- Document revisions keep their historical source IDs and evidence. Opening an old retained path preserves its actual revision, and a new projection does not overwrite old citation text.
- A full library export with retained documents includes a verified portable attachment bundle (`portableMaterials`). Restoring it into a fresh library restores the original bytes as well as the JSON and associations.

`materials.original.attach` adds an original to an existing document. It does not touch the document's text, revision, citations, selections or card links.

| Mode | What is stored |
| --- | --- |
| `copy` | A retained original (`version.attachment`) |
| `reference` | Nothing is copied. `version.external = { path, realPath, bytes, mtimeMs, hash, format, verifiedAt }` is stored, and the hash is streamed once at attach time |

Attach rules:

- **Before attaching**, the host compares the file with the stored text without a model (`materials.original.probe`). It checks the page count and the per-page similarity after the same whitespace folding the citation matcher uses.
- **A file that does not match** is attached only with `confirm: true`. The check is kept as `version.originalCheck`.
- **A text-only legacy document** gets a document record with exactly the identity it already had.
- **Reading a referenced original:** `materials.document.bytes` reads it only from its stored path, and only while it is still the verified file (same real path, size and hash). Otherwise it answers `{ status: "unavailable", reason: "missing" | "changed" | "redirected" | "unreadable", path }`.
- **No operation reads a path that the caller supplies at read time.**
- **Status and detach:** `materials.original.status` reports where an original stands, and `materials.original.detach` forgets it.
- **Backups:** a full export includes copies and lists referenced originals under `portableMaterials.referencedOriginals`. The referenced files themselves are not in the backup.

### Scoped writes

`Store.update(fn, changed, fields)` accepts an optional read/write projection: `fields` as an array, or `{ reads, writes }`.

- Scoped transactions on the current format decode only their declared inputs, reuse unmodified collection shards and commit one atomic manifest.
- Writes to an older format keep full migration and backup behaviour. Full unscoped updates keep their historical semantics.
- Cold loads still validate every shard, and damaged libraries stay write-protected.
- Transactions borrow the store's private working draft instead of cloning entire histories repeatedly. Read-only fields keep their mutation checks, and returned API objects stay detached.
- Shard reuse metadata comes from the committed working draft, not from mutable cached readers.
- Review operations keep the existing append-only attempt hint and run-ID hint.

## Extend StudyHub

### Add a capability

```js
const dispose = api.register({
  id: 'annotations', version: 1,
  collections: [{ name: 'annotations', mode: 'item' }],
  dependencies: ['materials.v1'],
  operations: {
    list: {
      input: { type: 'object', additionalProperties: false },
      description: 'Read saved annotations.',
      execute: async (_args, context) => ({
        annotations: (await context.state.read()).annotations,
      }),
    },
  },
});
```

- `register` adds the context to that library's runtime only.
- `context.state` reads detached owned data and merges only the declared fields on update.
- Dependency calls must be declared; built-ins also declare exact operation grants. Domain handlers never receive the whole `Store`.
- Your plugin may register its own typed DSH tools and UI contributions against these APIs. Release them through Cordis lifecycle ownership.

### Commit across contexts

- Register a read-validation participant with owned fields (`registerParticipant` on the runtime).
- Public invocation arguments carry data, never raw transactions or another context's mutable state.
- Treat durable schema changes separately from optional model-assisted enrichment.

### Run background work

Third-party operations get the same task service as built-ins:

```js
execute: (_args, context) => context.work.start({
  key: 'refresh-index', queue: 'index', label: 'Refresh index',
}, async ({ signal, progress }) => {
  signal.throwIfAborted();
  progress({ stage: 'Reading', done: 0, total: 1 });
  const result = await buildIndex({ signal });
  signal.throwIfAborted();
  return result;
})
```

- `start`, `get`, `list`, `wait` and `cancel` provide deduplication by `key`, FIFO queues, progress and detached results.
- `progress` accepts `stage`, `done`, `total` and `phase`.
- Scopes include both the domain and the work owner. Default queues are isolated by those identities.
- The completed history keeps the latest 100 tasks.
- Respect the supplied signal in long operations.

### Ownership of long-running work

- Unloading a domain aborts that domain's tasks. Unloading a host cancels only its own work.
- Captured state callbacks cannot commit after their context or host owner is removed, even when the same context ID is registered again.
- Request facades keep separate model routes and notifications. Sibling hosts can share installed capabilities without losing their own jobs when another workbench unloads.
- Live sessions, uploads, assist task histories, reusable teachers and panel bridges have explicit owners.
- Resume rebuilds upload paths from validated checkpoints rather than granting ownership to copied handles.

## Frontend modules

- **Entry.** The native entry (`ui/host.jsx`) loads the workspace seat (`ui/host/workspace.jsx`) and the document contributions (`ui/document-preview/native.jsx`).
- **Lazy views.** Optional views use seven lazy-loading boundaries in `ui/workspace-views.jsx`: `BlogNotes`, `Skeleton`, `Workflows`, `Graph`, `AudioDashboard`, `DocumentViewer` and `LiveClass`. The document viewer loads its page peek (`PagePeek`) lazily as well.
- **Page peek assets.** DSH serves a plugin's `client.*.js` chunks and no other file, so the page peek cannot point pdf.js at wasm, CMap or font URLs. `ui/document-preview/peek/assets/*.js` (made by `node scripts/pdf-assets.mjs --write` from `pdfjs-dist`; a test fails when they drift) are base64 modules that the build splits into chunks of their own, and `pdf-assets.js` hands them to pdf.js through its `BinaryDataFactory` when it asks: `jbig2.wasm` (JBIG2 and CCITT scans), `openjpeg.wasm` (JPX scans), the Symbol/ZapfDingbats fonts and the CMaps of four scripts. Nothing loads for a page without scans, and the reader and the start-up bundle do not contain them. A page whose images still fail to decode says so and offers the 原始 PDF tab instead of looking blank.
- **Live class.** `LiveClass` stays mounted when you navigate between views, so a recording keeps running.
- **Chunks.** `scripts/build.mjs` emits sibling `lib/client.<name>.js` classic factories through DSH's official `require.async` chunk protocol. All chunks use the host's React instance. Generated chunks are packaged and ignored by git; the authored boundaries live under `ui/`.
- **Standalone preview.** `npm run build` also builds `dist/app.js` and `dist/app.css` from `ui/dev.jsx`, as one script that includes the same lazy boundaries. `npm run dev` serves it.
- **Static demo.** `npm run build:demo` builds the static demo with ESM chunks (see [static demo](static-demo.md)).
- **Loader test.** `tests/client-boundaries.test.mjs` runs the real feature importers and checks the native preview and selection registrations.

### Interface strings

- Chinese is the source language. `ui(text)` looks up the English string in `ui/locales/en*.json`, whose keys are the Chinese strings.
- Each work package has its own English fragment, and `ui/i18n.js` imports and lists every fragment. `tests/wp1-i18n-fragments.test.mjs` fails when a file in `ui/locales/` is missing from that list.
