# 覆盖优先的出题（coverage-generation）

状态：设计，2026-10-05。依据：2026-10-05 的整条流程审计（`origin/main 95a7d56`）。范围只含核心链路：导入资料 → 生成题目 → 做题 → 反馈。

## 要解决的问题

学生拿一份很长的资料（例如 46–53 万字的双语转写）去出题，现在的行为是：

1. **覆盖不够。** 规划阶段只被「请求题数」限制：提示词是「最多抽取 N 个考点」，请求和回复里都没有「小节」。请求 15 题就只会得到约 15 个考点。实测：10 道保留的题只碰到 80 个部分里的 7 个（8.8%）。学生看不到这一点，只能在考试时发现没学到。
2. **重要性没有被利用。** 内容更长、AI 判断更重要的部分，没有得到更多的题。
3. **悄悄丢题。** 审阅回复格式坏了，整批（规划、定答案、出题的结果）被丢掉，不重试；失败的批次不参加自动补题轮次；原因在两处用两种说法写出来，其中一处是空话。
4. **30 题上限。** 它只限制覆盖，不保护成本：成本从 10 到 30 题几乎不变（见下表）。
5. **补题入口矛盾。** 草稿页上有「继续补齐 N 题」（从头重新规划，最少 20 次调用）和「补 N 题」（会把总目标抬高）两个互相无关的动作，却用同一个词。
6. **长任务不能暂停。** 出题任务的暂停是「不支持」；运行时限最多 60 分钟，超出就废。

## 验收标准（站在学生一边）

每一步都用这五条检查，而不只是测试通过：

1. 用带「标准答案清单」（每个小节的关键知识点）的样例资料，生成后按小节统计召回，漏的是哪些，要能列出来。
2. 学生**做题之前**就能看到哪些小节有题、哪些没有，不用猜。
3. 掌握度视图点名「从没出过题的小节」和「出了题但没做过的小节」，让学生考前知道哪里没学。
4. 从导入到第一次做题，学生需要做的决定和点击尽量少；「这份资料够不够、要不要补」由系统判断，不让学生判断。
5. 没有任何悄悄丢掉的东西：被丢弃的批次或题目有看得懂的真实原因，并且已经自动重试过。

## 数据和模型

**覆盖单位是小节。** 来源按优先级取：已保留的目录 → PDF 章节/页 → 录音转写里「第N部分」块（在录音一级之下）→ markdown 标题 → 约 8k 字的固定窗口。`英文原句` / `中文对照` 是标签，永远不是小节。

**每个小节有三种状态：**

- 已覆盖：至少一道保留下来的题的位置落在其中；
- 计划了但没成功：有一个持久化的计划考点落在其中，但没有保留的题，同时给出原因代码；
- 从未计划：两者都没有。

总体：已覆盖小节数 / 总小节数，加按字数加权的比例，以及每万字多少题。

**一个函数** `coverageOf(state, material, draftOrDeck)` 给四个地方用：任务页的「资料部分」（每个部分的范围和小条）、草稿页（「覆盖 7/80 部分 · 3 个计划了没出成」，一个按钮「为没覆盖的部分补题」，取代现在两个互相矛盾的入口）、资料页的行（覆盖标签）、阅读器目录（覆盖点，和掌握度圈并列）。

**需要补齐的数据**（现状里缺的）：

1. 后端的小节划分（`sectionsOf`，纯函数，放在 `lib`，阅读器的目录也用它）；
2. 每个生成切片的起止偏移（`batch.js` 的 `slices()` 现在切 6 万字的片，只保留来源 id，没有偏移）；
3. 每个部分的计划考点都要持久化，**包括整个失败的部分**（现在只存在内存的 `plans` 里，用完即丢）：`{targetId, part, sourceId, start, end, status, reason}`；
4. 题到部分的关联（题的 id 在 `assemble()` 里被重新随机，需要保留）。

## 成本事实

在 53.3 万字、9 个 6 万字分组的运行上测得：

| 阶段 | 次数 | 输入 token |
|---|---|---|
| plan | 9 | 142.5K |
| blueprint | 9 | 152.0K |
| author | 9 | 165.8K（+14.7K 缓存） |
| review | 9 | 161.4K |

98% 是输入，几乎都是同一份 6 万字原文在每个阶段重发。每个保留的题约 66K token。题数从 10 到 30，调用数几乎不变（40 → 40），所以 30 的上限不节省成本。不过：单次约不到 1 美分，成本不是主要问题，质量和覆盖才是。

可以砍的：blueprint / author / review 只发被引用的窗口（引文前后各约 3k 字）；双语只发原文语言；审阅回复坏了先重试一次；同一小节由同一个会话连续写题，提示词里「系统提示 + 小节原文」放最前面，保证前缀逐字节一致以命中缓存；审阅仍是独立会话，但共享同一前缀。

## 分阶段

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 1a | 审阅回复坏了先重试；失败的部分也参加补题；把所有「为什么没出题」的原因统一成同一个来源、写真话；持久化每个部分的计划考点和失败原因 | 无 |
| 1b | `sectionsOf`（小节划分）、切片偏移、阅读器目录只用真正的部分标题（修掉 `英文原句`/`中文对照` 变成条目的问题） | 无 |
| 2 | `coverageOf` + 四处视图 + 一个「为没覆盖的部分补题」 | 1a、1b |
| 3 | 覆盖强度三档（精简/标准/完整）+ 按小节规划 + 按长度和重要性分配题数 + 解除 30 题上限 + 估算 | 2 |
| 4 | 分批（wave）执行：每批存检查点，批与批之间可暂停，续跑，重启恢复，时限按批计算；证据上限随之放宽 | 3 |
| 5 | 缓存友好的运行方式（同一小节同一会话、前缀一致、只发被引用窗口）；任务记录持久化；标题「Recovered questions」改为真实标题 | 4 |

## 实现状态

- 阶段 1（1a、1b）：已实现，见 `docs/generation-reliability.md`。
- 阶段 2：已实现，见 [`docs/coverage.md`](../../coverage.md)：`lib/coverage.js` 的 `coverageOf`、`coverage.get`、四处视图（任务页「资料部分」、草稿页、资料页行和阅读器工具栏、阅读器目录）和唯一的「为没覆盖的部分补题」。
- 阶段 3a：已实现，见 [`docs/coverage.md`](../../coverage.md)「Coverage strength and enforced planning」：`lib/coverage-strength.js`（三档、配额、轮次）、`lib/section-weights.js`（每个部分的重要性）、`lib/assigned-plan.js`（服务端强制按分配规划，补问一次，仍不够记为 `plan-short`）、创建题组的「覆盖强度」和出发前的一行说明、草稿页的出题计划与每个部分的重要性和理由。第一次运行做第一轮，后面的轮次由 3b 执行；为没覆盖的部分补题按计划的配额继续。

- 阶段 3b：已实现，见 [`docs/coverage.md`](../../coverage.md)「Running the plan」：`lib/coverage-run.js`（轮次状态、每轮之后做什么、停止原因、数字和预计）和执行器（`lib/contexts/generation/operations.js`）。
  - 计划的各轮在同一份草稿上一轮接一轮做完，每轮是现有的补题（强制分配、不超过 30 题）；草稿是检查点（`editorial.coverageSpec.rounds[i].status` 和 `editorial.coverageRun`）。
  - 「自动补到完整」：精简默认关，标准和完整默认开；可选的花费上限；暂停于轮与轮之间；续跑；重启后「接着做」（同一个任务编号，进行中的那一轮从头重做）。
  - 运行时限按每一轮计（5–180 分钟），整个计划没有总时限。任务页顶部一行、资料部分里的轮次、日志里每一轮一行和停止原因；草稿页与首页行说同样的话。
  - 双语转写只按原文那一种语言数字数（`evidenceChars`）：标准档在样例上从约 343 题变为约 251 题。
  - 留给阶段 5 和统一任务运行时的：规划和出题提示词仍把译文一并发送；中断记录只在内存里，每次启动从草稿重建。

- 诚实的状态（2026-10-06 的学生视角评估）：已实现，见 [`docs/coverage.md`](../../coverage.md)「Honest states」：`lib/shortfall.js` 一个纯函数给首页横幅、待发布行、任务页和草稿页同一组数字和同一句话；进度是已出题数除以计划目标（短了就不是 100%）；每个状态只有一个主动作（接着做 / 继续 / 去配置模型 / 为没覆盖的部分补题）；密钥被拒绝是一句话并且可以接着做；最后一个计划轮没有新进展时先做有限的补做轮；反复失败的小节记在计划上、不再自动重试；「小节」是覆盖单位、「批次」是生成批次。
