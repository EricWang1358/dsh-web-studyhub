# 统一任务运行时：方案正文

> 2026-10-05 由仓库所有者批准。本文是目标设计，不表示已经实现或测试。实施前记录 `main` 的准确 commit SHA、现有行为和兼容范围，作为迁移基线（写进 sprint 文件）。

将出题、音频、PDF 转换、翻译、为你定制、每日总结等用户可见的后台工作，逐步接入同一个任务运行时。运行时统一管理任务身份、生命周期、资源调度、限流、调用追踪、计量、执行策略、恢复和控制台接口；各功能保留自己的步骤、业务约束、检查点内容和结果提交规则。

**实施节奏**：2.6.0 先交付任务控制台与公共契约，发布后按 P1–P6 迁移；每阶段可拆成多个独立可发布的 2.6.x 小版本。

**完成标准**：新增一种普通后台任务时，主要增加任务定义、业务执行器和必要的详情展示；公共查询、等待、控制、计量与控制台直接复用。

## 零、DSH 优先：复用宿主框架，不重新构建

StudyHub 是在 DSH（DeepSeek Harness）上的二次开发。这次重构要解决的正是"同一能力实现了好几遍"，所以**不能在插件里再造一套 DSH 已经提供的能力**。规则：

1. **先盘点，再设计。** 每个内核部件开工前，在 sprint 文件的「DSH 能力对照表」里写明：DSH 已有的对应接口（包名、服务名、方法、版本）、能否直接用、缺什么。只有 DSH 确实没有的部分才在插件里实现，并且实现为对 DSH 接口的**薄适配**。
2. **已知可复用的 DSH 能力**（以本地 DSH 0.2.0-rc.2 和 `node_modules/@deepseek-ai/*` 为准，实施时核对）：

   | 需要的能力 | 优先复用的 DSH 接口 | 现在插件里的位置 |
   |---|---|---|
   | 插件生命周期、服务注册、作用域释放、事件 | `@deepseek-ai/cordis` 上下文：`ctx.get` / `ctx.inject` / `ctx.on` / `ctx.effect`；`dsh-scope` | `lib/index.js`、`lib/runtime.js` |
   | 模型调用、模型配置与档位 | `ctx.llm.stream` / `resolveCallConfig` / `resolveModelInfo` / `listProviders`（`dsh-llm`） | `lib/index.js modelCompletion`、`lib/model-effort.js` |
   | 子代理（后台助手） | 宿主 `subagents.start` / `startContinuable` / `sendMessage` / `drainContinuableChildren`；会话 `ctx.sessions`；界面 `uiWorkspace.openSession` | `lib/host-capabilities.js`、`lib/generation-agent.js`、`ui/host/open-agent.js` |
   | 超时与取消 | `dsh-timeout`；标准 `AbortController` / `AbortSignal` | 各处 `AbortSignal.timeout`、`Promise.race` |
   | 契约与输入校验 | `schemastery`（DSH 插件配置同款） | `lib/runtime/domain-contracts.js` |
   | 插件任务服务 | `lib/runtime/tasks.js`（已为第三方扩展接入 `type:'extension'`）——审计它与 DSH 宿主任务/后台机制的关系 | `lib/runtime.js:199` |

3. **子代理一律走宿主的子代理服务**（显式 `executionMode`），不在插件里自建会话或模拟子代理；宿主做不到的（例如面板发起任务的子代理不进左侧会话列表，#213）在对照表里记录为宿主限制，不绕过。
4. **调度、计量、恢复如果 DSH 有对应机制**（例如宿主级并发限制、用量上报），优先接入；插件只补"按资源/配额域"的业务层规则。
5. **对照表是 PR 的必填项**：引入新的公共部件时，PR 描述必须引用对照表的对应行，说明"复用了什么 / 为什么必须自写"。审查按 [review-checklist.md](review-checklist.md) 核对。

## 一、为什么需要统一

现有调查覆盖 11 类后台任务。项目已有状态常量、共享 `jobs` 表、通用操作和 `lib/runtime/tasks.js`，但内置任务尚未共同使用完整的生命周期服务。

| 能力 | 现有分散位置 | 收敛目标 |
|---|---|---|
| 启动与收尾 | generation、selection、translation、audio、convert | 一个提交入口和生命周期管理者 |
| 并发与限流 | audio gate、PDF gate、coach slots、workflow、batch limiter、audio pool | 一套调度机制，按实际资源与配额域维护独立策略 |
| 推理档位 | stageEffortRoute、reasoningFor、correctionEffort、pickLightEffort（#226 后前两条已合并） | 一个解析入口，保留用途策略和 provider 参数映射 |
| 调用与计量 | generation steps、audio tracker、任务用量、每日账本、音频账本 | 共同调用记录和明确归属，按不同单位聚合 |
| 状态与恢复 | 音频、PDF、选区、daily、安装、实时校正 | 公共状态与恢复协议，各领域实现检查点 |
| 通知与展示 | 多处发信、按类型分支、独立轮询和任务卡 | 共同事件、快照和控制协议，模块提供专有详情 |
| 文件写入 | 多份原子 JSON 写入与 Windows 重命名重试 | 共用存储工具，保留经过验证的平台行为 |

迁移清单以具体调用点和责任边界为准。近期故障与某份重复实现之间的因果关系，应通过复现和测试确认。

纳入范围的是需要独立查询、等待、控制或恢复的后台工作。实时课堂连接继续由会话子系统管理，其后台校正、保存和出题接入任务运行时；普通即时请求、缓存和小型去重结构按原有职责管理。

## 二、目标架构与职责边界

以 `lib/jobs/` 作为统一任务运行时的入口，审计并演进现有 `lib/runtime/tasks.js`、`lib/runtime/work.js`、`lib/job-status.js`、`lib/model-effort.js`、`lib/audio-pool.js`。迁移期保留 extension 和旧业务入口的兼容层，最终形成一个生命周期实现。

| 部件 | 公共运行时负责 | 业务模块保留 |
|---|---|---|
| 契约与注册表 | 类型、版本、输入校验、操作和能力声明 | 任务名称、业务参数和结果类型 |
| 生命周期 | 创建、状态转换、执行身份、停止与结算 | 业务完成条件、部分结果和停止收尾 |
| 调度器 | 资源许可、互斥、排队、公平性、冷却和动态限额 | 所需资源、单元并发、数据依赖 |
| 模型网关 | 执行模式、推理解析、provider 适配、调用计量和追踪 | 提示词、用途、格式校验和业务修复 |
| 非模型执行适配器 | 转录、转换、安装等外部操作的调用与控制协议 | 工具参数、结果解释和远端状态核对 |
| 存储与恢复 | 元记录、版本、检查点引用、原子写入和恢复调度 | 检查点含义、输入快照、已完成单元与提交规则 |
| 观测与通知 | 公共快照、调用时间线、输出读取、通知投递 | 阶段名称、结果摘要、专有详情和链接 |

任务定义以 `run(ctx, input)` 为基本入口。`ctx` 提供取消信号、步骤追踪、进度、资源申请、执行网关和检查点访问。批量任务使用共同的有限并发工具；有序窗口、草稿补齐、跨步骤依赖继续在业务模块中表达。

核心只依赖公共契约，具体任务通过注册接口接入（注册与生命周期挂在 cordis 上下文上，插件卸载时随作用域释放）。UI 详情组件在前端注册，运行时输出可序列化数据。

业务模块不得自行建立第二套任务生命周期、直接修改公共状态或私自结算任务。一个执行尝试的资源释放、状态持久化和完成事件，由运行时统一协调。

## 三、任务身份和控制语义

### 1. Job、Attempt、Step、Call

| 对象 | 含义 |
|---|---|
| **Job** | 用户发起的一次逻辑工作；重试或恢复后保留 `jobId` |
| **Attempt** | 一次执行尝试；有 `attemptId`、执行者、策略快照和起止记录 |
| **Step** | 有稳定 `stepKey` 的逻辑单元，例如音频窗口或翻译批次；每次执行可有 `stepRunId` |
| **Call** | 网关能够观测的一次实际外部请求；重试、hedge 和 fallback 分别记录 |

Step 与 Call 不要求一一对应。宿主内部请求不可见时，标明观测边界，不伪造请求数量。

同一个 scope 中，每个 Job 在任一时刻只允许一个活动 attempt；不同 Job 按资源和业务互斥规则并发。一个 attempt 只结算一次；旧 attempt 的迟到回调、进度和结果不能覆盖新 attempt；结果提交点校验当前执行身份与业务版本；重试和恢复保留历史尝试。

### 2. 生命周期与业务结果分开

```text
queued  running  pausing  paused  cancelling  cancelled  complete  failed  interrupted
```

旧 `done` 映射为 `complete`；`interrupted` 表示失去执行者；部分结果用 `result.completeness`；`superseded` 用结束原因或结果有效性表达。失败、取消或中断都可能保留部分结果。

公共接口：`submit`、`status`、`list`、`wait`、`control`、`output`。现有 `job.cancel` 等保留为兼容入口。`job.control` 承载取消、暂停、继续、重试及任务支持的其他动作，合法性由内核根据能力和当前状态判断。

### 3. 暂停

任务声明 `pauseMode: unsupported | queued-only | checkpoint` 与 `recoveryMode: none | retry-from-start | resume-checkpoint`。检查点暂停：停止派发新单元 → 已接纳单元到达安全边界 → 保存检查点 → 释放资源、结束当前 attempt → `paused`。继续时保留 `jobId`、创建新 attempt、从检查点执行。到达安全边界前保持 `pausing` 并显示等待原因。不具备有效检查点的路径不声明运行中暂停。

### 4. 取消与超时

取消先进入 `cancelling`，停止派发、传播取消信号、阻止后续普通结果提交；模块可在受控收尾阶段提交允许的部分结果。远端操作无法确认停止时保留操作引用和已知状态。区分排队期限、执行总预算、单次请求超时；超时触发实际停止协议，`Promise.race` 返回不能证明底层已停止。

## 四、调度、执行策略和计量

### 1. 按资源与实际配额域调度

| 资源 | 典型范围 |
|---|---|
| 模型调用并发与请求频率 | provider 的实际配额域（账户、项目或模型组） |
| 音频转录槽位 | 现有 host 级范围 |
| 本地转换与安装 | 工具、设备或安装目录 |
| 资料与草稿写入 | library、document 或 draft |
| 单任务内部并发 | batch、window 或 member |

一套调度实现，多个资源实例各自维护限制；并发许可、请求频率、429 冷却和业务互斥分别建模；同一配额域共享限流反馈。动态调整只影响后续派发；自动回升不超过配置上限；退避时释放槽位，到期重新申请；provider 槽位只在实际调用期间占用；父任务不能占满槽位后再等待同一资源的子任务；首版简单公平派发、有界等待。解除翻译与出题串行前，先核对资料、草稿和保存顺序，单独验收。

### 2. 重试

执行适配器标准化错误和 provider 重试信息（含 `Retry-After`），区分暂时性限流、额度耗尽、网络失败、永久错误、业务格式错误。网络重试、格式修复、任务重跑分别计数并受总次数、时间、预算约束。**同一次请求只有一个责任层做传输重试。** 有副作用的远端请求只在幂等键或结果核对支持时自动重发；恢复时先核对 `remoteOperationId`。

### 3. 模型网关

受管模型请求统一进入网关，显式声明 `purpose`、`feature`、`requestedEffort`、`executionMode`（`direct` / `agent-preferred` / `agent-required`）、`budget`。`jobId` 只负责归属。推理优先级：合法的单次调用设置 → 用户任务设置 → 任务类型策略 → 系统默认；先解析语义档位，再由 provider 适配器映射参数，记录请求档位、实际参数和回退原因。子代理命名、能力检测、登记、状态关联和取消传播在共同执行层处理（调用宿主子代理服务）；直接调用也进入时间线。每日总结和学习流的子代理优先单独开关启用。

### 4. 计量

调用记录是计量事实来源，按 Job、Attempt、Step、feature 聚合到任务用量与每日账本；音频时长、tokens、请求数、费用按各自单位记录，保留音频额度检查语义；重试、hedge 败方、fallback 都留记录；未知用量标 `unknown` / `estimated`；每日账本按调用发生时间归属，恢复旧任务不重复入账；宿主汇总与 provider 明细的权威关系写明。

## 五、持久化与控制台契约

| 数据 | 保存责任 |
|---|---|
| 类型、输入引用、attempt、状态、版本、策略、检查点引用 | 公共任务存储 |
| 草稿、翻译段落、音频窗口、转换产物和提交记录 | 原有领域存储 |
| controller、Promise、连接和当前执行 handle | 当前进程内存 |
| 调用日志与输出尾部 | 有上限的观测存储 |

音频和 PDF 已有 manifest 先通过适配器接入；公共原子写入器保留 Windows 重命名重试。公共快照与旧 manifest 不能同时决定生命周期。恢复前验证输入可访问、指纹匹配、版本兼容、原执行者已退出、已完成单元可核对；只把确认失去执行者的 attempt 标为 `interrupted`。首版每个 scope 一个运行时管理者，可并发多个 Job；跨进程执行需另行设计。恢复可以重复执行未确认的工作，产物用稳定 operation key / stepKey / 提交记录去重，重点覆盖"产物已提交、检查点未保存时崩溃"。完成事件与待通知状态持久记录，投递用稳定事件键去重；通知失败不改变任务完成状态。`dismiss`、历史清理与产物删除分别定义。

控制台（P0）先消费兼容适配器输出的**版本化**公共契约（见 `docs/job-contract.md`）：身份与当前 attempt、状态/阶段（结构化 code）/进度（`total` 可空）、可用动作与不可用原因、结果引用与错误、用量与执行方式、类型专有详情；调用时间线记录可观测的排队/开始/首段输出/结束时间（缺失就留空）；`job.output` 用游标读取（`nextCursor`、截断标记），UI 遇缺口重读快照。

## 六、迁移顺序与阶段验收

每阶段可拆成多个 2.6.x。每类任务先接入公共机制并核对原行为，再单独启用新能力。迁移期旧实现必须登记在例外清单；已接入路径只有一个调度、重试、计量和结算责任层。

- **P0 任务控制台（2.6.0）**：契约首版、适配器接入现有任务、能力反馈、游标输出。
- **P1 内核最小闭环**：演进 `tasks.js`；注册、身份、生命周期、资源许可、执行入口、元记录、统一结算；**单文件音频导入**为试点，经既有 manifest 适配恢复；试点与旧路径**共享同一资源/配额域的计数与冷却**。验收：提交、排队、调用、进度、计量、取消、通知、重启识别闭环；无双重调度/重试/计量；新旧并存时总并发与配额约束成立。
- **P2 音频完整迁移**：可恢复导入 → 批量与窗口 → 字幕导入 → 校对复查 → 课堂保存；admitAudio 等迁入调度器，原子写入迁入公共存储；`orderedWindows` 保留领域语义、替换重复并发。
- **P3 出题家族**：出题、补题、选区补题、修题、发布；先接现有队列，再做稳定步骤标识、检查点与提交核对；验收重启可见并可继续、不重复提交、补题不被当成新建、fill rounds 与 reserve pool 回归。
- **P4 翻译与其他模型任务**：翻译、为你定制（#234）、每日总结、学习流、助手；分别开关：翻译解除不必要串行、子代理优先、按天聚合。
- **P5 非模型任务**：PDF 转换、Marker 安装、MinerU 配置、检索索引；远端创建与安装不被通用重试无条件重复。
- **P6 清理与护栏**：删除无使用者的旧实现；新增普通任务不需改核心类型分支；例外清单清零或逐项说明。

## 七、测试与协作护栏

按能力验收（所有任务：身份、状态转换、查询、能力声明、一次结算、终态保护；取消；暂停；恢复；受限服务的配额与 429；模型与子代理；UI 沿用 #208 布局检查、缩放与窄屏）。核心测试用可控执行器、模拟 provider、假时钟和故障注入，重点覆盖迟到写回、提交前后崩溃、重复恢复、并发 429、重试叠加、输出截断、动态下调并发。真实模型抽检作为发布证据（固定输入/模型/策略，记录质量、耗时、请求数、用量、样本范围，有预算）。

架构约束用模块依赖与 API 边界检查执行；迁移期登记旧入口、负责人和移除阶段，禁止新增未登记旁路。公共契约与核心模块有唯一合并负责人，功能迁移代理只用已发布接口，接口缺口先提契约变更。界面先出设计稿；开发用 `test:fast`，全量测试排队并在发布门禁执行。细则见 [agent-rules.md](agent-rules.md)。

## 八、兼容、切换和回退

1. 先提供读取兼容，再启用新写入或新执行策略。
2. 按任务类型或 scope 切换入口，开关默认只影响新提交。
3. 已启动 attempt 固定执行者、任务定义版本和必要配置；动态资源限额作为调度设置单独生效。
4. 运行中任务完成后切换，或在兼容检查点停止并明确交接。
5. 回退前停止新入口接纳，排空在途任务或保存检查点；新版本才能理解的任务保留记录和产物。
6. 回退验收分别验证：能回退启动、既有产物可读、未完成新任务能否继续。

新增恢复、解除翻译串行、切换子代理各自有独立开关、验收和回退说明。每个版本只对已验证范围承诺可回退。
