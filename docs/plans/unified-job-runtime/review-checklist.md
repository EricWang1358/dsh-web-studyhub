# 合并前审查清单（统一任务运行时）

每个相关 PR 合并前，审查者逐条回答“是 / 否 / 不适用”，并附源码、测试或评审证据，写进 PR 评论。任何“否”都需要说明并由所有者决定；“不适用”须给出范围理由，尚未验证不能标为不适用。S1-0 的通过评审是 S1-1 的硬前提，不能靠其他条目通过来抵消。文档 PR 不声明运行测试、宿主能力或实施门禁已通过。

## 思想是否被贯彻

1. **DSH 优先**：新增公共部件是否引用能力表行 ID、实际版本和核验来源？能复用的是否复用了同一服务实例？自写缺口是否有证据与明确适配边界，而非把“待核验”当成“不支持”？
2. **一处实现**：这次接入后，相关路径是否只有一个调度、一个传输重试层、一个用量入账点、一个结算者？有没有留下第二套（包括"临时"的）？
3. **业务与内核分工**：内核是否没有出现某个功能的业务判断（按类型的 if/else、功能专有字段）？业务模块是否没有自建生命周期、直接改公共状态或私自结算？
4. **契约优先**：新接口是否先改了契约文档并单独合并？契约版本与兼容说明是否更新？
5. **行为保持**：特征测试在开关开/关下是否都通过？行为改进是否有独立开关、验收和回退说明？

## 正确性

6. 一次结算、取消/完成竞态、迟到进度与产物写回保护、卸载收尾是否有测试？排队期限、执行预算、请求超时是否传播实际停止信号，许可是否在真实占用结束后仅释放一次？
7. 声明的能力（暂停、恢复、取消、重试）是否真实可用？不支持的能力是否如实拒绝、UI 没有假按钮？
8. 恢复是否覆盖产物提交前、产物提交后检查点保存前、检查点保存后终态/通知保存前的崩溃与重复恢复？是否核对产物、提交记录、输入指纹、版本和原执行者？远端结果未知时是否先核对而非自动重发？
9. 用量是否只记一次、按调用时间归属、未知值标为 unknown/estimated？
10. 并发：转写是否复用宿主许可，文本是否按已核验的录音/批次/实际配额域范围验证？新旧路径共享策略的总上限、双向 429 冷却、一次申请、取消清理、退避释放、动态下调与回升是否有实际占用断言？扩大限制作用域是否独立开关，而非随试点隐式启用？

## 体验与质量

11. 观测不到的数据是否留空而不是编造？
12. UI 改动是否有设计稿、通过布局跳动检测、在 100%/150% 缩放与 1280/420 宽度下截图核对？
13. 受影响路径是否做了真实模型抽检并记录？

## 工程卫生

14. 实现/缺陷测试是否有红灯记录，特征测试是否在旧实现上通过？代码 PR 的 `npm run verify` 是否全绿、新慢测试是否登记？文档 PR 是否验证链接、范围与前后要求一致，并如实标明未运行代码测试？
15. 没有碰所有者的学习库、`~/.dsh`、密钥；测试环境清空了密钥变量？
16. 文档、接手记录、已合并 PR、验证 SHA 与证据是否一致？新增能力是否有独立开关和验证，实施步骤是否没有被文档 PR 提前勾选？
17. 切换是否只影响新提交，在途 attempt 是否保持执行者、定义版本与策略快照？发布是否有指定回退 tag/SHA 的演练，分别记录旧版启动、产物可读、未完成新任务能否继续的结果？
