## 两项新增测试为什么必要

1. **AU-06 的观察者语义**：现有成功/失败/取消测试多直接等到终态，没有明确把等待查询的上限与任务执行期限区分。新测试让 fake transcription 保持未完成，等待真实 public job.wait 返回后检查它仍在运行；随后解除同一请求并验成品、manifest、逻辑/尝试身份、通知、课程和不出题。测试使用条件等待与 API 自己的观察者上限，不用固定延时推测状态。
2. **AU-14 的运行中重启**：已有 audio-single-process fixture 先进入 failed 终态再新建进程，无法证明 host 退出时未结算请求会变成可继续的卡片。新 fixture 在公共 snapshot 确认 running、转写请求保持未决、初始 manifest 已可读取后直接结束真实进程；第二个进程先读取卡片（零模型请求），再调用显式 retry。断言保留 failed 兼容显示、逻辑 ID、不保留旧尝试卡、未完成请求不能冒充已完成缓存。

## 执行与交接

- 新测试与 fixture 已集成到 alpha 工作树，按 cli 调度类别运行。
- 测试输入只是一秒合成 PCM WAV，课程和 provider 响应均为测试造数，不进入真实业务数据；fake fetch 遇到非转写请求立即报错，不能落回真实网络。
- 两项测试都在自己的临时 library 和 DSH_HOME 内工作；所有子进程使用 windowsHide，清理先终止并等子进程结束，再删除明确创建的临时目录。复用 tests/helpers/wait.mjs 的 until/settleJob。
- 新增 2 项均通过。完整测试、宿主探针和复跑结果见 [基线记录](s1-0-baseline.md)；源码观察不能替换执行证据。
- 没有确认的新生产缺陷。AU-14 的 failed 映射属于既有兼容事实；AU-08 的非统一 host 文字额度及 AU-20 的恢复保证是已有边界，不在此单元实现。任何运行失败由父代理记录原断言和环境，本阶段不顺手改生产。
