# 陪学与追问等待时间优化

用户提供的真实请求：coach.nudge 4.878–13.593 秒、coach.reply 2.444–4.331 秒、card.translate 3.587–7.757 秒、card.followup.suggest 43.734 秒、snapshot 1.156 秒。工作区解析均为 0 ms。原日志只记录 action 总耗时，不能证明具体瓶颈是模型首字、生成、重试还是存储。

本次保留当前未提交改动，在当前分支优化（用户明确批准）；不更换模型、不调用真实付费模型、不提交或发布。

改动：

- 同一陪学记录并发的 confused 请求合并。完成后再次点击仍能获得下一种解释。
- 推荐问题按题目内容和问答历史缓存到卡片；并发请求合并，重开面板或重启服务均可复用。题目或问答变化后失效，旧请求不能写入新版缓存。
- 翻译和追问只有一层纠错重试。此前 JSON 解析失败会在内外两层分别重试，最多调用四次；现在最多两次。追问的传输错误不做格式纠错重试。
- 推荐问题和追问答案提供输出预算；仅在宿主支持关闭推理时传递 token 上限，避免截断仍需推理的模型。沿用原有模型与最低推理设置。
- 模型慢请求日志增加配置、首段文本等待、文本生成、总耗时，不记录题目、回答或凭据。snapshot 慢请求增加读取与构建耗时。
- 翻译并发键包含内容摘要，拒绝保存改题前的过期翻译。

## 可复现测量

运行 `node scripts/measure-study-latency.mjs`，使用临时学习库及固定 100 ms 的模拟模型，无外部网络调用。

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 两个同时到达的 confused 请求 | 2 次模型调用，保存 2 条，179 ms | 1 次模型调用，保存 1 条，141 ms |
| 同组推荐连续请求五次 | 无缓存，每次调用模型（代码路径确认） | 共 1 次调用，127.4 / 0.6 / 0.7 / 0.6 / 0.6 ms |
| 持续无效 JSON | 嵌套重试最多 4 次 | 测试确认最多 2 次 |

时间是单次诊断样本，优化的主要证据是调用次数和缓存行为，不能解释为真实模型的延迟改善百分比。微型学习库 snapshot 完整读取约 4.25 ms、未变化轮询约 1.09 ms；未在用户的大型真实学习库上复现 1.156 秒，因此未据此修改存储策略。

剩余限制：首次请求仍依赖模型服务；需要用新版 `[study-model]` / `[study-snapshot]` 日志区分剩余延迟。推荐缓存没有主动预生成，避免无请求时新增模型消耗。
